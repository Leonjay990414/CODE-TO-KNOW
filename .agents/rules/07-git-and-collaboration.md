\# 07 — Git and Team Collaboration Rules

\# 碼上學｜CODE TO KNOW

\# Git 版本控制與團隊協作規則



\## 1. 文件目的



本文件規範 CODE TO KNOW 專案的 Git 版本控制、GitHub 遠端儲存庫管理、分支策略、Commit 命名、多人協作與程式碼整合流程。



所有參與專案的開發人員與 AI Agent 都必須遵守本文件，確保程式碼可以追蹤、版本可以回復、多人工作不互相覆蓋。



\## 2. 核心原則



1\. 所有重要程式碼與文件都必須納入版本控制。

2\. 每次 Commit 必須具有清楚且具體的修改目的。

3\. 不得將未完成或未驗證的程式碼直接合併至正式分支。

4\. 不得覆蓋其他成員尚未提交的工作。

5\. 不得將 API Key、密碼、Token 或個人機密資料推送至 GitHub。

6\. 每次重大修改前應確認目前分支與工作目錄狀態。

7\. 所有遠端同步操作都必須確認執行結果。

8\. AI Agent 不得未經授權自行執行破壞性 Git 操作。



\## 3. GitHub 專案管理



專案遠端儲存庫：



`https://github.com/Leonjay990414/CODE-TO-KNOW`



主要分支：



`main`



目前儲存庫設定為 Private。



GitHub 儲存庫主要用途：

\- 保存專案原始碼。

\- 保存品牌與產品規格文件。

\- 保存 Rules 與 Skills。

\- 追蹤開發歷史。

\- 協助多人協作。

\- 提供版本回復依據。



GitHub 儲存庫的公開或私人設定，不代表未來網站的公開或私人狀態。



\## 4. 分支管理策略



\### 4.1 main



`main` 為主要穩定分支。



用途：

\- 保存已整合的專案內容。

\- 保存經過必要驗證的版本。

\- 作為正式發布的基礎。



禁止事項：

\- 不得直接推送未完成的大型功能。

\- 不得將未經測試的重大修改直接合併。

\- 不得任意重寫主要分支歷史。



\### 4.2 feature 分支



新功能應使用獨立分支。



命名格式：



`feature/功能名稱`



例如：

\- `feature/student-dashboard`

\- `feature/question-bank`

\- `feature/ai-tutor`

\- `feature/teacher-management`



\### 4.3 fix 分支



錯誤修正使用：



`fix/問題名稱`



例如：

\- `fix/login-validation`

\- `fix/api-response`

\- `fix/mobile-layout`



\### 4.4 docs 分支



大型文件修改可使用：



`docs/文件主題`



例如：

\- `docs/brand-guidelines`

\- `docs/system-architecture`



小型文件更新可依專案工作流程直接提交至目前分支。



\### 4.5 分支使用原則



\- 每項大型功能應使用獨立分支。

\- 分支名稱必須容易理解。

\- 完成後應經過測試與整合。

\- 不再使用的分支應適時清理。

\- 不得任意刪除其他成員仍在使用的分支。



\## 5. Commit 命名規範



Commit 訊息使用簡潔、明確的英文格式。



建議格式：



`type: description`



允許使用的類型：



\- `feat:` 新增功能。

\- `fix:` 修正錯誤。

\- `docs:` 文件更新。

\- `style:` 不影響程式邏輯的格式調整。

\- `refactor:` 程式碼重構。

\- `test:` 新增或修改測試。

\- `chore:` 專案設定與維護工作。

\- `perf:` 效能改善。

\- `build:` 建置流程或套件設定。

\- `ci:` 持續整合流程修改。



範例：



`feat: add student dashboard`



`fix: correct login validation`



`docs: update project rules`



`test: add question bank tests`



`chore: update dependencies`



Commit 應遵守：

\- 一次 Commit 盡量只處理一個主要目的。

\- 不使用沒有意義的訊息，例如 update、test123。

\- 不應將多個無關功能混在同一個 Commit。

\- 不得宣稱已完成實際尚未完成的功能。



\## 6. 標準 Git 工作流程



\### 6.1 開始工作前



先確認目前位置與分支：



`pwd`



`git branch --show-current`



`git status`



確認遠端是否有新版本：



`git fetch origin`



若目前工作目錄乾淨，且準備開始新的工作，可同步：



`git pull --ff-only origin main`



若工作目錄存在尚未提交的修改，應先檢查並妥善保存，不得直接覆蓋。



\### 6.2 開始功能開發



建立功能分支：



`git switch -c feature/功能名稱`



如果分支已存在，先確認其內容，再切換至該分支。



開發期間應定期檢查：



`git status`



\### 6.3 完成修改後



先檢查修改內容：



`git diff`



檢查尚未追蹤的檔案：



`git status`



加入需要提交的檔案：



`git add 檔案路徑`



檢查即將提交的內容：



`git diff --cached`



建立 Commit：



`git commit -m "type: description"`



\### 6.4 推送遠端



第一次推送新分支：



`git push -u origin 分支名稱`



後續推送：



`git push`



推送完成後確認：



`git status`



\### 6.5 整合回 main



功能完成後，應先確認：

\- 功能符合需求。

\- 必要測試已執行。

\- 沒有未解決的重大錯誤。

\- 沒有機密資料。

\- 沒有其他成員尚未整合的衝突。



優先透過 GitHub Pull Request 進行審查與整合。



小型個人專案可依實際情況使用本機整合流程，但不得跳過必要測試。



\## 7. Pull Request 與程式碼審查



Pull Request 應包含：



1\. 修改目的。

2\. 修改內容。

3\. 涉及的功能或文件。

4\. 執行過的測試。

5\. 可能影響的其他模組。

6\. 已知問題或待處理事項。



審查時應確認：

\- 是否符合專案規則。

\- 是否符合品牌與 UI 規範。

\- 是否存在安全性問題。

\- 是否有重複或不必要的程式碼。

\- 是否影響原有功能。

\- 是否有適當測試。

\- 是否更新必要文件。



不得只因程式可以執行，就直接認定程式碼品質合格。



\## 8. 多人協作規則



團隊成員應遵守：



1\. 每個人應清楚知道自己負責的工作。

2\. 不同成員應盡量使用不同功能分支。

3\. 修改共用檔案前應先確認是否有人正在處理。

4\. 不得任意覆蓋其他成員的程式碼。

5\. 重要架構修改應先溝通。

6\. 發現衝突時應先確認修改目的。

7\. 合併前應完成必要測試。

8\. 不得將個人帳號密碼或 Token 分享給其他成員。



建議透過 GitHub Issues、Pull Requests 或專案任務文件追蹤工作。



\## 9. Merge Conflict 衝突處理



發生合併衝突時：



1\. 停止直接推送或覆蓋。

2\. 查看衝突檔案。

3\. 確認雙方修改的目的。

4\. 比較修改前後的內容。

5\. 決定保留、整合或重新設計的方式。

6\. 完成衝突處理。

7\. 執行相關測試。

8\. 確認沒有遺失必要功能。

9\. 完成 Commit 並推送。



不得在不了解內容的情況下，直接選擇全部保留本地或全部採用遠端版本。



\## 10. Git 安全與禁止操作



以下操作具有較高風險，執行前必須先確認影響範圍：



\- `git reset --hard`

\- `git clean -fd`

\- `git push --force`

\- `git branch -D`

\- `git rebase`

\- 修改或重寫已推送的 Commit 歷史。



AI Agent 不得未經使用者明確授權執行上述破壞性操作。



禁止事項：

\- 不得提交 `.env`。

\- 不得提交 API Key。

\- 不得提交資料庫密碼。

\- 不得提交使用者個人資料。

\- 不得提交不必要的建置產物。

\- 不得提交大型暫存檔。

\- 不得任意修改 `.gitignore` 以繞過安全限制。



若發現機密資訊已經推送，應立即停止繼續使用該機密，並依安全流程進行撤銷與更換。單純刪除檔案不代表歷史紀錄中的機密已消失。



\## 11. .gitignore 管理



以下類型通常不應提交：



\- `node\_modules/`

\- `.env`

\- `.env.local`

\- `.env.\*.local`

\- `dist/`

\- `build/`

\- `.kagent/`

\- 作業系統暫存檔。

\- IDE 個人設定。

\- 測試產生的暫存資料。

\- 本機資料庫與私人測試資料。



實際忽略規則應依專案架構調整。



不得忽略重要的原始碼、設定範本、文件或必要測試檔案。



可以提交不含真實密鑰的環境變數範本，例如 `.env.example`。



\## 12. 版本回復



若修改造成問題，應先分析影響範圍。



優先使用不重寫既有歷史的方式回復：



`git revert Commit編號`



若尚未提交的修改需要保留，可考慮使用：



`git stash`



但執行前應先確認工作目錄狀態。



不得在沒有備份或確認的情況下，直接重置或刪除其他成員的工作。



正式發布版本應保留可追蹤的版本紀錄。



\## 13. Tag 與版本標記



重大版本可使用 Git Tag 標記。



建議版本格式：



`MAJOR.MINOR.PATCH`



例如：



\- `v0.1.0`：初期原型。

\- `v0.2.0`：新增重要功能。

\- `v1.0.0`：第一個正式穩定版本。



版本意義：

\- MAJOR：重大架構或相容性變更。

\- MINOR：新增功能。

\- PATCH：錯誤修正與小型更新。



版本號應反映實際完成程度，不得提前宣稱正式發布。



\## 14. 文件與程式碼同步



以下內容應保持一致：



\- `README.md`

\- `AGENTS.md`

\- `PROJECT\_RULES.md`

\- `.agents/rules/`

\- `.agents/skills/`

\- `docs/`

\- 實際程式碼與設定。



若功能規格或系統架構發生重大變化，應同步更新相關文件。



不得讓文件持續描述已經不存在的功能或錯誤架構。



\## 15. AI Agent 工作規則



AI Agent 在 Git 操作時必須：



1\. 先確認目前工作目錄。

2\. 確認目前分支。

3\. 檢查工作目錄是否乾淨。

4\. 了解修改內容。

5\. 不得任意刪除使用者檔案。

6\. 不得覆蓋未提交的修改。

7\. 不得提交機密資料。

8\. 使用符合規範的 Commit 訊息。

9\. 推送前確認修改範圍。

10\. 推送後確認遠端同步結果。

11\. 遇到衝突時先分析，不得擅自選擇覆蓋方向。

12\. 執行高風險操作前必須取得使用者明確同意。

13\. 不得在沒有實際執行的情況下宣稱推送成功。



\## 16. 最終原則



Git 不只是保存程式碼的工具，也是 CODE TO KNOW 專案的重要協作與品質管理基礎。



每次修改都應留下清楚紀錄，每次整合都應經過合理確認，每個版本都應能追蹤與管理。



\*\*保持版本清楚、協作透明、修改可追蹤，讓專案能夠穩定持續成長。\*\*

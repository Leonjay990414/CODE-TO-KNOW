\# 03 — Backend and API Development Rules

\# 後端與 API 開發規範



\## 1. 規範目的



本文件定義「碼上學｜CODE TO KNOW」後端服務與 API 的開發原則。



後端負責處理平台核心業務邏輯、使用者身分驗證、角色權限、資料存取及前後端資料交換。



所有後端功能都必須以安全性、穩定性、可維護性及可擴充性為核心。



\---



\## 2. 後端開發核心原則



1\. 所有重要業務邏輯應由後端負責處理。

2\. 不得只依靠前端判斷使用者身分或權限。

3\. 所有外部輸入都必須經過驗證。

4\. API 必須具有明確的輸入及輸出格式。

5\. 敏感資料必須受到適當保護。

6\. 不得將資料庫密碼、API Secret 或其他機密資訊寫入公開程式碼。

7\. 不得讓未授權使用者存取受保護的資料。

8\. 所有重要操作都應有適當的錯誤處理。

9\. 後端程式碼應保持模組化，避免所有功能集中在單一檔案。

10\. 不得以假資料或模擬結果冒充正式功能。



\---



\## 3. 後端架構原則



實際後端框架、程式語言、伺服器及部署方式，統一於第 8 階段確認。



架構設計應考慮以下功能層：



\### 3.1 API 層

負責接收前端請求、檢查請求格式、呼叫對應服務及回傳結果。



\### 3.2 業務邏輯層

負責處理平台功能，例如課程管理、考試管理、題庫操作及學習紀錄。



\### 3.3 資料存取層

負責與資料庫溝通，避免業務邏輯直接依賴特定資料庫細節。



\### 3.4 驗證與權限層

負責確認使用者身分、角色及操作權限。



\### 3.5 共用服務層

負責管理通知、郵件、檔案處理及其他共用功能。



實際分層方式可依最終技術架構調整，但必須保持責任清楚。



\---



\## 4. API 設計規範



所有 API 應具備一致的設計方式。



\### 4.1 命名原則



\- 使用容易理解的英文名稱。

\- 路徑應能表達資源或功能。

\- 同類型 API 應保持命名一致。

\- 避免使用沒有明確意義的縮寫。

\- 依照 HTTP Method 表達操作意圖。



\### 4.2 HTTP Method



| Method | 用途 |

|---|---|

| GET | 取得資料 |

| POST | 新增資料或執行特定操作 |

| PUT | 完整更新資料 |

| PATCH | 部分更新資料 |

| DELETE | 刪除資料 |



實際使用時，應依照資源操作的語意選擇適當方法。



\### 4.3 API 回應格式



API 應使用統一且容易理解的資料格式。



建議基本結構：



```json

{

&#x20; "success": true,

&#x20; "message": "操作成功",

&#x20; "data": {}

}

```



錯誤回應範例：



```json

{

&#x20; "success": false,

&#x20; "message": "請求資料不正確",

&#x20; "error": {

&#x20;   "code": "VALIDATION\_ERROR"

&#x20; }

}

```



不得在正式錯誤回應中暴露資料庫密碼、伺服器路徑、堆疊追蹤或其他內部機密資訊。



\---



\## 5. 使用者帳號與身分驗證



平台預計支援不同使用者角色：



\- 學生

\- 教師

\- 管理員



帳號系統必須遵守：



1\. 每個帳號具有唯一且可識別的使用者身分。

2\. 密碼不得以明文方式儲存。

3\. 密碼應使用適當的密碼雜湊演算法處理。

4\. 登入時必須驗證帳號與密碼。

5\. 必須處理登入失敗及帳號異常情況。

6\. 必須具備安全的登出機制。

7\. 必須處理登入狀態逾時。

8\. 密碼重設流程必須驗證使用者身分。

9\. 不得在錯誤訊息中洩漏不必要的帳號資訊。

10\. 必須避免暴力嘗試登入及大量異常請求。



若使用第三方登入服務，必須由後端驗證第三方提供的身分憑證，不可只相信前端傳入的使用者資料。



\---



\## 6. 角色與權限管理



平台必須採用後端權限驗證。



\### 6.1 學生權限



預計可執行：



\- 查看個人資料。

\- 使用已開放的課程。

\- 進行題庫練習。

\- 參加指定考試。

\- 查看個人學習紀錄。

\- 使用 AI 學習輔助。

\- 查看個人成就與點數。



\### 6.2 教師權限



預計可執行：



\- 管理授權班級。

\- 查看所屬學生資料。

\- 建立及管理題目。

\- 建立及管理考試。

\- 發布班級公告。

\- 查看學生學習紀錄。

\- 管理補考及考試安排。



\### 6.3 管理員權限



預計可執行：



\- 管理使用者帳號。

\- 管理使用者角色。

\- 管理平台內容。

\- 管理系統設定。

\- 檢視必要的系統紀錄。



\### 6.4 權限驗證原則



1\. 每個受保護的 API 都必須檢查使用者身分。

2\. 每項操作都必須確認角色及資源存取權限。

3\. 教師只能操作獲得授權的班級及資料。

4\. 學生不得存取其他學生的私人紀錄。

5\. 一般使用者不得自行提升帳號權限。

6\. 前端隱藏按鈕不能視為權限保護。

7\. 權限變更應由後端執行並留下必要紀錄。



\---



\## 7. 資料驗證與輸入處理



所有 API 輸入資料都必須進行驗證。



驗證項目包括：



\- 必填欄位。

\- 資料型態。

\- 字串長度。

\- 數值範圍。

\- 日期與時間格式。

\- 電子郵件格式。

\- 使用者角色。

\- 資料關聯性。

\- 使用者是否具有操作權限。



必須注意：



1\. 不可直接信任前端傳入的資料。

2\. 不可直接將使用者輸入拼接成 SQL 指令。

3\. 應使用安全的資料庫查詢方式。

4\. 必須防範 SQL Injection。

5\. 必須防範不安全的檔案上傳。

6\. 必須避免未經驗證的資料進入資料庫。

7\. 錯誤資料應回傳適當提示。



\---



\## 8. 資料庫操作原則



後端負責統一管理資料庫存取。



1\. 不得讓前端直接連接資料庫。

2\. 資料新增、修改及刪除必須經過權限驗證。

3\. 重要資料操作應考慮交易處理。

4\. 必須避免重複建立不必要的資料。

5\. 必須考慮資料完整性及關聯性。

6\. 不得任意刪除重要學習紀錄。

7\. 必要時應保留資料異動紀錄。

8\. 資料庫錯誤不得直接暴露給一般使用者。

9\. 必須規劃資料備份與還原機制。

10\. 資料庫結構變更應有版本管理方式。



\---



\## 9. 重要業務功能



後端應支援平台主要業務功能。



\### 9.1 課程管理

管理課程、單元、教材及課程開放狀態。



\### 9.2 題庫管理

管理題目、選項、答案、解析、分類及難度。



\### 9.3 考試管理

管理考試時間、考試對象、作答紀錄、評分及補考設定。



\### 9.4 學習紀錄

保存學生練習、測驗、作答時間及學習進度。



\### 9.5 教師管理

管理教師帳號、班級、學生及教學操作權限。



\### 9.6 通知管理

處理平台公告、系統通知及必要的電子郵件通知。



\### 9.7 AI 服務

由後端統一管理 AI 服務呼叫，避免將 AI API 金鑰暴露於前端。



以上功能須依正式需求規格逐步實作，不得只建立空白 API 就標示為完成。



\---



\## 10. 錯誤處理與系統紀錄



後端必須具備一致的錯誤處理機制。



錯誤類型包括：



\- 請求格式錯誤。

\- 未登入。

\- 權限不足。

\- 找不到指定資料。

\- 資料衝突。

\- 請求過於頻繁。

\- 外部服務異常。

\- 資料庫連線錯誤。

\- 系統內部錯誤。



紀錄原則：



1\. 必要的系統錯誤應留下紀錄。

2\. 重要管理操作應保留稽核資訊。

3\. 不得在紀錄中保存明文密碼。

4\. 不得記錄完整的私密金鑰或存取憑證。

5\. 紀錄內容應有適當的存取限制。

6\. 必須避免紀錄敏感個人資料。



\---



\## 11. API 安全性



所有後端服務都必須考慮以下安全措施：



\- HTTPS 傳輸。

\- 身分驗證。

\- 角色權限驗證。

\- 輸入資料驗證。

\- 登入及 API 請求頻率限制。

\- 安全的 Cookie 與工作階段設定。

\- CORS 合理設定。

\- 防範常見 Web 攻擊。

\- 機密資訊環境變數管理。

\- 必要的稽核紀錄。



不得將所有 API 設定為公開存取。



不得只因前端不顯示某個功能，就認為該 API 不需要權限保護。



\---



\## 12. 外部服務串接



平台可能串接：



\- AI 模型服務。

\- Google 身分驗證。

\- 電子郵件服務。

\- 檔案儲存服務。

\- 其他教育相關服務。



串接原則：



1\. 外部服務憑證必須由後端安全管理。

2\. 必須處理外部服務逾時。

3\. 必須處理外部服務失敗。

4\. 必須避免短時間大量重複請求。

5\. 必須考慮使用額度及費用。

6\. 不得假設外部服務永遠可用。

7\. 未完成串接的服務不得標示為正式啟用。



\---



\## 13. 效能與穩定性



1\. 避免不必要的資料庫查詢。

2\. 大量資料應考慮分頁。

3\. 必要時使用快取。

4\. 避免單一請求執行過多工作。

5\. 外部服務呼叫應設定合理逾時。

6\. 重要服務應考慮異常恢復。

7\. 必須避免未處理的例外造成服務中斷。

8\. 應依照實際使用情況評估效能。



\---



\## 14. 測試與驗收



每項後端功能完成後，必須確認：



1\. API 可以正常運作。

2\. 輸入驗證符合預期。

3\. 成功及失敗回應正確。

4\. 未登入使用者無法存取受保護功能。

5\. 不同角色的權限符合規格。

6\. 不同使用者無法任意存取彼此的資料。

7\. 資料庫新增、修改及查詢結果正確。

8\. 外部服務失敗時有適當處理。

9\. 沒有明顯的伺服器錯誤。

10\. 不會影響既有功能。



涉及權限及安全性的功能，必須額外進行負面測試，確認未授權操作確實會被拒絕。



\---



\## 15. AI Agent 開發規則



AI Agent 執行後端任務時，必須：



1\. 先閱讀專案規則及相關文件。

2\. 先確認既有 API 與資料結構。

3\. 不得任意更換後端技術。

4\. 不得擅自移除既有 API。

5\. 不得將重要權限驗證只放在前端。

6\. 不得在程式碼中寫入真實機密資訊。

7\. 修改資料庫結構前，必須確認影響範圍。

8\. 新增 API 時應同步更新相關文件。

9\. 完成後應提供測試結果。

10\. 不得宣稱未經實際測試的功能已完成。

11\. 發現安全性問題時，應優先處理。

12\. 遇到重要規格不明確時，應先詢問確認。



\---



\## 16. 最終開發原則



後端是「碼上學｜CODE TO KNOW」平台的核心。



所有後端服務與 API 都必須符合：



\*\*安全、穩定、可靠、可維護、可擴充。\*\*



使用者資料、學習紀錄、考試結果及教師管理功能，都必須受到適當保護。



任何功能都不能只追求能夠執行，更必須確保執行結果正確且符合權限規範。

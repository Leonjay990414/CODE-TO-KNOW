# CODE TO KNOW — Antigravity Project Instructions

## 1. Project Identity

- Chinese brand: 碼上學
- English brand: CODE TO KNOW
- Full name: 碼上學 AI 智慧學習與教育科技平台
- Slogan: 碼上學，學無止境。
- English tagline: Learn Beyond Limits.
- This is a new independent project.
- Never mix this project with the previous CodeSolv project.

## 2. Project Mission

Build an AI-powered education platform integrating:

- Academic learning and theoretical knowledge
- Practical exercises and skill development
- Question banks and mock examinations
- AI explanations, hints and troubleshooting
- Courses and learning resources
- Learning progress and personalized assistance
- Educational games and interactive experiences
- Student, teacher and administrator functions

AI should support independent thinking, not replace it.

## 3. Development Principles

1. Read the existing project files before modifying anything.
2. Follow the current project structure.
3. Do not create duplicate files or unnecessary folders.
4. Do not replace existing implementations without understanding their purpose.
5. Do not invent completed features, APIs, credentials or integrations.
6. Explain important architectural decisions before making major changes.
7. Prefer maintainable, secure and modular implementations.
8. Keep the website responsive across desktop, tablet and mobile devices.
9. Do not install unnecessary packages.
10. Test affected functionality after making changes.

## 4. Brand and UI Guidelines

The product should feel like a premium, modern education technology platform.

Visual direction:

- Clean and refined

- Light color palette
- Consistent spacing and typography
- Clear information hierarchy
- Smooth but restrained animations

## 5. Technical Constraints

- Do not assume the technology stack is finalized.
- Follow the approved architecture and technical decisions once documented.
- Do not introduce a new framework or database without approval.
- Keep frontend, backend, database and AI responsibilities clearly separated.
- Validate data on the server side.
- Never expose API keys or secrets in frontend code.
- Use environment variables for sensitive configuration.
- Follow secure authentication and authorization practices.

## 6. Database and User Permissions

- Design data structures according to actual product requirements.
- Separate student, teacher and administrator permissions.
- Never trust role information supplied only by the frontend.
- Validate access permissions on the server.
- Protect personal information and learning records.
- Do not use real user data for development testing.

## 7. AI Feature Guidelines

- AI responses should be relevant to the learning context.
- Provide hints and explanations that encourage independent thinking.
- Do not claim that an AI feature works without a real integration.
- Handle API failures and unavailable services gracefully.
- Avoid presenting uncertain AI-generated information as verified facts.

## 8. File and Documentation Management

- Follow FOLDER_STRUCTURE.md.
- Follow PROJECT_RULES.md.
- Follow TEAM_WORKFLOW.md.
- Follow PROJECT_TRACKER.md.
- Follow the relevant documents under docs/.
- Update documentation when important project decisions change.
- Use clear and consistent file names.

## 9. Git and Version Control

- Use the main branch for stable project versions.
- Use descriptive Conventional Commit messages.
- Do not commit secrets, credentials or local agent data.
- Review changed files before committing.
- Do not overwrite or discard existing work without permission.

## 10. AI Agent Working Procedure

Before implementing a task:

1. Understand the requested outcome.
2. Inspect relevant files and existing implementations.
3. Identify dependencies and possible impacts.
4. Propose a clear implementation plan for major changes.
5. Implement only the approved scope.
6. Run appropriate checks and tests.
7. Summarize modified files and test results.
8. Identify unfinished work and limitations.

If requirements are unclear, ask before making assumptions.

## 11. Definition of Done

A task is complete only when:

- The requested implementation is present.
- Existing functionality is not unintentionally broken.
- Relevant tests or checks have been performed.
- Documentation is updated when necessary.
- No secrets or unrelated files are included.
- Remaining limitations are clearly reported.

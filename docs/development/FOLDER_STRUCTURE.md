# CODE TO KNOW｜專案資料夾架構與管理規範

**文件名稱：** FOLDER_STRUCTURE.md  
**專案名稱：** 碼上學｜CODE TO KNOW  
**文件用途：** 統一專案資料夾架構、檔案分類與命名方式。

---

## 1. 專案根目錄

所有專案程式碼、文件與素材，原則上統一存放於專案根目錄。

```text
CODE-TO-KNOW/
├── ai/
├── backend/
├── branding/
├── database/
├── docs/
│   ├── planning/
│   ├── architecture/
│   └── development/
├── frontend/
├── games/
├── public/
├── scripts/
├── tests/
├── .gitignore
└── README.md
```

## 2. 資料夾用途

| 資料夾 | 用途 |
| --- | --- |
| ai/ | AI 模型串接、提示詞、AI 輔助學習功能 |
| backend/ | 後端 API、伺服器與業務邏輯 |
| branding/ | Logo、品牌識別、色彩、字體及品牌素材 |
| database/ | 資料庫結構、資料表設計及資料管理 |
| docs/ | 專案規劃、技術架構及開發文件 |
| frontend/ | 網站前端、頁面、元件及使用者介面 |
| games/ | 學習遊戲、互動練習及遊戲系統 |
| public/ | 公開圖片、圖示及網站靜態素材 |
| scripts/ | 自動化腳本、維護及部署工具 |
| tests/ | 單元測試、整合測試及系統測試 |

## 3. 文件分類

docs/ 下依文件性質分類：

- planning/：品牌規劃、產品規劃、專案管理與需求文件。
- architecture/：系統架構、技術選型、資料流程與 API 設計。
- development/：開發規範、資料夾規範、程式碼管理與協作流程。

## 4. 檔案命名規則

1. 資料夾名稱原則上使用英文小寫。
2. 多個英文單字以連字號 `-` 分隔。
3. 文件名稱使用清楚且具體的英文名稱。
4. Markdown 文件使用 `.md` 副檔名。
5. 程式檔案依所使用的語言及框架慣例命名。
6. 避免使用 `final`、`new`、`test2` 等不明確名稱。
7. 不可隨意覆蓋重要文件或程式碼。

## 5. 新增功能時的檔案放置原則

- 新增 AI 功能，優先放入 ai/。
- 新增網站介面，優先放入 frontend/。
- 新增伺服器功能，優先放入 backend/。
- 新增資料表或資料庫設計，放入 database/。
- 新增學習遊戲，優先放入 games/。
- 新增測試程式，放入 tests/。
- 新增品牌素材，放入 branding/。
- 新增專案說明文件，依照文件類型放入 docs/ 對應資料夾。

若功能同時涉及多個模組，應先確認主要責任歸屬，再決定檔案位置。

## 6. 文件與程式碼管理

1. 不將密碼、API 金鑰或私人憑證提交至 GitHub。
2. 環境設定與程式碼分開管理。
3. 不隨意刪除或移動其他模組的檔案。
4. 變更資料夾架構時，應同步更新本文件。
5. 新增主要模組時，應補充用途與管理說明。

## 7. 架構調整原則

本文件為專案初期的規劃架構。

未來正式選定前端框架、後端技術及部署方式後，可以依實際需求增加子資料夾，但應維持分類清楚、責任明確及容易維護的原則。

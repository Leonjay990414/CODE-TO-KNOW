# CODE TO KNOW｜兩人團隊分工與專案協作規範

**專案名稱：** 碼上學｜CODE TO KNOW  
**團隊規模：** 2 人  
**文件版本：** 1.0

---

## 1. 團隊管理原則

本專案採用兩人協作開發模式。

每項工作應指定主要負責人，另一位成員負責協助、檢查或提供建議。

兩位成員皆須了解專案整體架構，不應讓重要功能只有單一成員能夠維護。

## 2. 成員角色與工作職責

### 成員 A｜專案與介面設計負責人

主要工作：

- 專案進度規劃與追蹤。
- 品牌識別及視覺規範管理。
- UI/UX 使用者體驗設計。
- 網站頁面與互動流程規劃。
- 前端介面協作開發。
- 文件整理及版本紀錄。
- 協助系統測試與問題回報。

### 成員 B｜系統與技術開發負責人

主要工作：

- 前端技術架構協作。
- 後端 API 與伺服器開發。
- 資料庫架構與資料管理。
- AI 模型及服務串接。
- 系統安全與權限管理。
- 部署及技術環境管理。
- 協助系統測試與問題修正。

### 共同工作

兩位成員共同負責：

- 學習功能與題庫規劃。
- AI 教學體驗。
- 學習遊戲及互動功能。
- 功能測試與品質檢查。
- 重大技術決策。
- 專案成果驗收。

## 3. 任務分配規則

每項任務應記錄：

1. 任務名稱。
2. 任務內容。
3. 主要負責人。
4. 協作人員。
5. 預計完成日期。
6. 目前進度。
7. 驗收結果。

任務狀態統一使用：

- 尚未開始
- 進行中
- 等待檢查
- 已完成
- 遇到問題

## 4. 每週進度管理

每週至少進行一次進度確認。

確認項目：

- 本週完成的工作。
- 尚未完成的工作。
- 遇到的技術問題。
- 下週預計完成的工作。
- 是否需要重新分配任務。

重要決策應留下文字紀錄，避免只透過口頭討論。

## 5. GitHub 版本管理

兩位成員共同使用 GitHub 私有 Repository。

基本原則：

1. `main` 分支只保留可正常使用的穩定版本。
2. 新功能應使用獨立分支開發。
3. 完成功能後先進行測試及程式碼檢查。
4. 確認沒有重大問題後再合併至 `main`。
5. Commit 訊息應清楚描述修改內容。
6. 不可將密碼、API 金鑰或私人資料提交至 GitHub。

建議分支命名：

- `feature/功能名稱`
- `fix/問題名稱`
- `docs/文件名稱`

## 6. 問題回報與修正流程

發現問題時，應記錄：

- 問題發生位置。
- 問題描述。
- 重現方式。
- 預期結果。
- 實際結果。
- 負責修正的人員。

修正完成後，由另一位成員協助確認結果。

## 7. 工作交接原則

當主要負責人暫時無法處理工作時，另一位成員應能透過文件、程式碼註解及 Git 紀錄理解目前進度。

重要功能應保留必要的技術說明。

## 8. 完成標準

一項工作必須符合以下條件，才可標記為完成：

- 已完成預定功能。
- 基本測試通過。
- 沒有已知的重大錯誤。
- 相關文件已更新。
- 程式碼已提交至正確分支。
- 必要時經另一位成員檢查。

# 身分驗證與安全架構設計文件（AUTHENTICATION & SECURITY ARCHITECTURE）

- 品牌名稱：碼上學｜CODE TO KNOW
- 文件版本：1.0
- 文件狀態：架構規劃
- 文件路徑：`docs/architecture/AUTHENTICATION_SECURITY_ARCHITECTURE.md`
- 適用平台：Web、Android、iOS、Windows、macOS
- 核心原則：安全驗證、最小權限、資料隔離、個資保護

---

## 1. 文件目的

本文件定義碼上學平台的身分驗證、帳號管理、角色權限、資料存取及系統安全機制。

平台預計服務學生、教師及管理員，因此必須確保：

1. 使用者只能登入自己的帳號。
2. 使用者只能操作被授權的功能。
3. 學生不能讀取其他學生的私人學習資料。
4. 教師只能管理獲授權的班級及學生。
5. 管理員的高權限操作必須受到保護。
6. 前端不得自行決定使用者角色或權限。
7. API 必須在伺服器端重新驗證身分及權限。
8. 使用者個人資料及登入憑證必須受到保護。

本文件為安全架構規劃，不代表相關安全功能已經完成實作或通過安全測試。

## 2. 身分驗證整體架構

### 2.1 系統流程

```text
使用者
  │
  ▼
前端登入介面
  │
  ▼
Backend Authentication API
  │
  ├── 驗證帳號及登入方式
  ├── 驗證密碼或 Google ID Token
  ├── 檢查帳號狀態
  ├── 建立登入 Session
  │
  ▼
Session／Cookie 管理
  │
  ▼
後端權限驗證
  │
  ├── Student
  ├── Teacher
  └── Admin
  │
  ▼
授權後的 API 與資料
```

### 2.2 安全設計原則

- 身分驗證與權限驗證分開處理。
- 所有權限判斷必須由後端執行。
- 不信任前端傳入的角色、使用者 ID 或教師電子郵件。
- 使用 HTTPS 保護傳輸過程。
- 登入憑證不得直接暴露在 URL。
- 不將密碼或 Token 寫入一般日誌。
- 重要操作必須留下稽核紀錄。

## 3. 使用者角色與權限

### 3.1 角色定義

| 角色 | 代碼 | 主要權限 |
| --- | --- | --- |
| 學生 | STUDENT | 課程、練習、考試、AI 助教、個人學習紀錄 |
| 教師 | TEACHER | 班級管理、教材、考試、作業、學生學習分析 |
| 管理員 | ADMIN | 平台管理、帳號管理、角色審核及系統設定 |

未來可依實際需求擴充學校管理員等角色。

### 3.2 學生權限

學生可以：

- 查看自己的個人資料。
- 加入已授權的班級。
- 查看有權使用的課程及教材。
- 進行練習與測驗。
- 查看自己的作答紀錄。
- 查看自己的學習分析。
- 使用 AI 學習助教。
- 查看自己的點數及徽章。

學生不得：

- 查看其他學生的私人學習資料。
- 修改自己的角色為教師或管理員。
- 修改其他學生的考試紀錄。
- 存取未授權班級。
- 直接讀取未公開的正確答案。

### 3.3 教師權限

教師可以：

- 建立或管理授權範圍內的班級。
- 查看所屬班級成員。
- 建立課程作業。
- 設定考試及測驗。
- 查看班級成績。
- 發布班級公告。
- 查看授權學生的學習分析。

教師不得：

- 任意管理其他教師的班級。
- 修改管理員權限。
- 任意查看不屬於其管理範圍的學生資料。
- 未經授權修改其他教師建立的考試。
- 透過修改前端請求取得額外權限。

### 3.4 管理員權限

管理員可以依職務授權：

- 管理使用者帳號。
- 審核教師身分。
- 管理角色與權限。
- 管理學校及班級資料。
- 檢視系統運作狀態。
- 管理平台設定。
- 查看必要的系統稽核紀錄。

管理員權限應採最小權限原則，不應讓所有管理員都擁有不必要的資料存取能力。

## 4. 帳號註冊系統

### 4.1 註冊方式

第一階段規劃：

- 電子郵件註冊。
- 密碼設定。
- 電子郵件驗證。
- 個人顯示名稱。
- 使用者角色申請。

未來可評估其他第三方登入方式。

### 4.2 註冊流程

```text
進入註冊頁面
    │
    ▼
輸入電子郵件與密碼
    │
    ▼
後端驗證輸入內容
    │
    ▼
檢查電子郵件是否已註冊
    │
    ▼
建立待驗證帳號
    │
    ▼
寄送驗證信
    │
    ▼
使用者完成電子郵件驗證
    │
    ▼
帳號啟用
    │
    ▼
進入平台
```

### 4.3 密碼安全

- 不得以明文儲存密碼。
- 使用 Argon2id 或經評估的安全密碼雜湊方案。
- 每個密碼雜湊應使用獨立 Salt。
- 不得自行設計密碼加密演算法。
- 設定合理的密碼長度與強度要求。
- 密碼重設必須透過安全驗證流程。
- 不得透過電子郵件直接寄送使用者原始密碼。

### 4.4 電子郵件驗證

驗證流程應具備：

- 隨機且不可預測的驗證 Token。
- Token 有效期限。
- Token 單次使用限制。
- 驗證成功後立即失效。
- 重新寄送驗證信的頻率限制。

驗證 Token 應以安全方式保存，避免資料庫遭讀取時直接取得可使用的驗證憑證。

## 5. Google Identity Services 登入

### 5.1 設計目的

支援使用者透過 Google 帳號登入，降低註冊及登入操作的複雜度。

### 5.2 登入流程

```text
使用者點擊 Google 登入
    │
    ▼
Google Identity Services
    │
    ▼
取得 Google ID Token
    │
    ▼
傳送至後端驗證
    │
    ▼
後端驗證 Token
    │
    ├── 簽章
    ├── 發行者 Issuer
    ├── 有效期限
    ├── Audience
    └── 使用者識別資訊
    │
    ▼
確認或建立平台帳號
    │
    ▼
檢查帳號狀態與角色
    │
    ▼
建立平台 Session
    │
    ▼
登入成功
```

### 5.3 Google 登入安全要求

- 必須由後端驗證 Google ID Token。
- 驗證 Token 的簽章及有效期限。
- 確認 Audience 與平台設定的 Client ID 相符。
- 不得只相信前端傳入的 Google 電子郵件。
- 不得將 Google ID Token 當成平台自己的 Session Token。
- 第三方登入帳號應使用穩定的 Google 使用者識別碼建立關聯。
- 帳號綁定及解除綁定必須有安全驗證流程。

### 5.4 教師 Google 登入

Google 登入成功不代表使用者自動成為教師。

教師角色必須經過平台核准。

流程：

1. 使用者完成 Google 登入。
2. 使用者提出教師身分申請。
3. 後端建立待審核申請。
4. 管理員透過管理介面審核。
5. 核准後由後端授予 TEACHER 角色。
6. 記錄審核人員及時間。

不得透過前端傳入 `teacherEmail` 或 `role=TEACHER` 就直接授予教師權限。

## 6. Session 與 Token 管理

### 6.1 管理原則

平台應優先採用安全的伺服器端 Session 或經完整安全設計的 Token 機制。

若使用 JWT：

- 使用安全的簽章演算法。
- 驗證 Token 簽章及有效期限。
- 設定合理的 Token 有效時間。
- 建立安全的更新與撤銷機制。
- 不在前端公開保存長期有效的憑證。
- 不接受未經驗證的 Token Claims。

### 6.2 Cookie 安全設定

Web 平台使用 Cookie 時，建議設定：

- HttpOnly：避免前端 JavaScript 直接讀取。
- Secure：只透過 HTTPS 傳送。
- SameSite：依登入流程設定適當策略。
- Path：限制 Cookie 適用路徑。
- Max-Age 或 Expires：設定合理有效期限。

Cookie 設定必須與前後端網域及部署環境配合。

### 6.3 Session 管理

系統應支援：

- 登入後建立 Session。
- 登出後使 Session 失效。
- 密碼變更後撤銷適當的既有 Session。
- 帳號停用後阻止繼續使用。
- 管理員撤銷可疑 Session。
- 必要時提供使用者查看及管理登入裝置的功能。

### 6.4 CSRF 防護

若使用 Cookie 進行身分驗證，應依部署方式加入 CSRF 防護。

包括：

- CSRF Token 或適當的雙重提交策略。
- SameSite Cookie。
- Origin／Referer 檢查。
- 對狀態變更 API 進行驗證。

不得只依賴 CORS 作為 CSRF 防護。

## 7. 角色授權系統

### 7.1 RBAC

採用 Role-Based Access Control（角色型存取控制）。

基本概念：

```text
User
  │
  ▼
UserRole
  │
  ▼
Role
  │
  ▼
Permission
  │
  ▼
API Authorization
```

### 7.2 權限判斷

每個受保護 API 都必須執行：

1. 驗證登入狀態。
2. 取得伺服器端確認的使用者身分。
3. 檢查角色。
4. 檢查功能權限。
5. 檢查資源所屬關係。
6. 執行操作。
7. 必要時留下稽核紀錄。

### 7.3 資源層級權限

僅有角色檢查並不足夠。

例如教師雖然具有 TEACHER 角色，但仍必須確認：

- 該教師是否屬於該班級。
- 該考試是否由其建立或獲授權管理。
- 該學生是否屬於其管理範圍。
- 該教材是否允許其修改。

因此，必須同時實施資源層級的存取控制。

## 8. 班級與學生資料隔離

### 8.1 核心原則

每次查詢班級、學生、成績或學習紀錄時，後端都必須確認使用者的資料存取範圍。

### 8.2 學生資料

學生只能查看：

- 自己的學習紀錄。
- 自己的考試結果。
- 自己的 AI 對話。
- 自己的點數及成就。
- 已授權的班級與課程。

### 8.3 教師資料

教師只能查看：

- 自己授權的班級。
- 班級內的學生資料。
- 授權範圍內的考試紀錄。
- 授權範圍內的學習分析。

### 8.4 防止 IDOR

系統不得只因使用者提供某個資料 ID，就允許讀取或修改該筆資料。

每次操作都必須驗證：

- 使用者身分。
- 資料擁有者。
- 資源所屬班級。
- 使用者角色。
- 目前操作是否被授權。

## 9. API 安全架構

### 9.1 基本要求

- 所有受保護 API 必須進行身分驗證。
- 使用 Zod 或適當驗證工具檢查輸入。
- 使用統一錯誤回應格式。
- 設定請求頻率限制。
- 限制請求內容大小。
- 防止 SQL Injection。
- 防止 XSS。
- 防止 CSRF。
- 限制 CORS 允許來源。
- 不向外部回傳資料庫內部錯誤及機密資訊。

### 9.2 輸入驗證

所有輸入資料都必須視為不可信任。

包括：

- 使用者 ID。
- 班級 ID。
- 考試 ID。
- 題目 ID。
- 角色名稱。
- 電子郵件。
- 上傳檔案。
- AI 請求內容。

後端不得直接相信前端傳入的權限資訊。

### 9.3 錯誤處理

建議統一錯誤格式：

```json
{
  "success": false,
  "error": {
    "code": "FORBIDDEN",
    "message": "您沒有權限執行此操作。"
  }
}
```

正式環境不得將 Stack Trace、資料庫連線資訊或機密設定直接傳給使用者。

## 10. 常見安全風險防護

| 安全風險 | 防護方式 |
| --- | --- |
| 暴力破解登入 | Rate Limiting、異常登入監控 |
| 密碼外洩 | 安全雜湊、密碼重設流程 |
| SQL Injection | ORM、參數化查詢、輸入驗證 |
| XSS | 輸出編碼、內容安全政策 |
| CSRF | CSRF Token、Cookie 安全設定 |
| IDOR | 資源擁有權驗證 |
| 權限提升 | 後端角色與權限驗證 |
| Session 劫持 | HTTPS、安全 Cookie、Session 撤銷 |
| Token 外洩 | 安全保存、短效憑證、撤銷機制 |
| 機密外洩 | 環境變數及機密管理 |
| 檔案上傳攻擊 | 檔案類型、大小及內容檢查 |
| API 濫用 | Rate Limiting、額度限制 |

## 11. 密碼重設與帳號恢復

### 11.1 密碼重設流程

```text
使用者提出重設申請
    │
    ▼
輸入註冊電子郵件
    │
    ▼
系統建立一次性重設 Token
    │
    ▼
寄送重設連結
    │
    ▼
使用者完成身分驗證
    │
    ▼
設定新密碼
    │
    ▼
後端更新密碼雜湊
    │
    ▼
撤銷適當的既有 Session
    │
    ▼
完成重設
```

### 11.2 安全要求

- 不直接顯示電子郵件是否存在的敏感資訊。
- 重設 Token 必須隨機且不可預測。
- 設定有效期限。
- 僅能使用一次。
- 不將新密碼透過電子郵件傳送。
- 完成重設後使重設 Token 失效。

## 12. 帳號狀態與審核

帳號狀態規劃：

| 狀態 | 說明 |
| --- | --- |
| PENDING_VERIFICATION | 等待電子郵件驗證 |
| ACTIVE | 正常使用 |
| SUSPENDED | 暫時停用 |
| DISABLED | 已停用 |
| PENDING_REVIEW | 等待角色或身分審核 |

不同狀態必須對應不同的登入與操作限制。

教師審核應保存：

- 申請者 ID。
- 申請時間。
- 審核者 ID。
- 審核結果。
- 審核時間。
- 必要的審核備註。

## 13. 個人資料與隱私保護

### 13.1 最小資料蒐集

平台應只收集提供服務所需的資料。

不應因為技術方便而任意蒐集學生的敏感個人資訊。

### 13.2 學習資料保護

- 學生個人學習紀錄應有存取限制。
- 教師只能取得教學所需資料。
- AI 服務只接收必要的上下文。
- 對外部服務傳送資料前評估去識別化需求。
- 不得公開學生個人排名或學習資料，除非具備適當授權與明確用途。

### 13.3 資料保存

應依適用法規及平台政策制定：

- 帳號資料保存期限。
- 學習紀錄保存期限。
- AI 對話保存期限。
- 登入紀錄保存期限。
- 稽核紀錄保存期限。
- 刪除及備份資料的處理方式。

## 14. 檔案上傳安全

平台未來可能支援 PDF、圖片及其他教材上傳。

安全要求：

- 限制允許的檔案格式。
- 限制檔案大小。
- 驗證 MIME Type 及實際檔案內容。
- 使用安全的檔案名稱及儲存識別碼。
- 不直接執行使用者上傳的檔案。
- 檔案下載前檢查使用者權限。
- 私人教材不得使用公開可猜測的網址。
- 必要時使用病毒或惡意檔案掃描服務。

## 15. 稽核與安全監控

### 15.1 重要操作

以下操作應留下稽核紀錄：

- 登入及登出。
- 登入失敗。
- 密碼重設。
- 角色變更。
- 教師審核。
- 班級成員異動。
- 考試設定修改。
- 成績修改。
- 管理員操作。
- 帳號停用及恢復。

### 15.2 日誌安全

不得記錄：

- 明文密碼。
- 完整 Session Token。
- API Key。
- 私密驗證資訊。
- 不必要的個人敏感資料。

### 15.3 異常事件

系統應能識別並記錄：

- 短時間大量登入失敗。
- 異常 API 請求。
- 不合理的權限操作。
- 大量資料存取。
- 不正常的 Token 使用情況。

對高風險事件可觸發管理員通知或暫時限制操作。

## 16. 安全測試與驗收

### 16.1 身分驗證測試

- [ ] 一般帳號可以正常註冊。
- [ ] 電子郵件驗證流程正常。
- [ ] Google 登入由後端驗證。
- [ ] 錯誤密碼無法登入。
- [ ] 停用帳號無法使用受保護功能。
- [ ] 密碼重設流程正常。
- [ ] 登出後 Session 失效。

### 16.2 權限測試

- [ ] 學生不能取得教師功能。
- [ ] 學生不能取得管理員功能。
- [ ] 教師只能管理授權班級。
- [ ] 教師不能自行提升管理員權限。
- [ ] 管理員權限受到保護。
- [ ] 修改前端角色資料不能改變後端權限。

### 16.3 資料隔離測試

- [ ] 學生不能讀取其他學生的私人資料。
- [ ] 教師不能查看未授權班級。
- [ ] 未授權使用者不能修改考試。
- [ ] 不同使用者的 AI 對話互相隔離。

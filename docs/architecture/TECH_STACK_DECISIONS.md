# 技術選型與決策紀錄（TECH STACK DECISIONS）

**專案名稱：** 碼上學｜CODE TO KNOW  
**專案全名：** 碼上學 AI 智慧學習與教育科技平台  
**文件路徑：** `docs/architecture/TECH_STACK_DECISIONS.md`  
**文件用途：** 確立平台開發所採用的主要技術、選擇理由、使用範圍及未來擴充方向。

---

## 1. 技術選型目標

本專案需要建立一套可持續擴充的 AI 教育平台，第一階段以響應式網站為核心，未來逐步支援 Android、iOS、Windows 及 macOS。

技術選型必須符合：

1. 適合小型開發團隊維護。
2. 能支援學生、教師及管理員等不同角色。
3. 能處理課程、題庫、考試及學習紀錄。
4. 能安全串接 AI 模型及外部服務。
5. 具備資料庫、身分驗證及權限管理能力。
6. 支援自動化測試及版本控制。
7. 能逐步擴充至跨平台應用程式。
8. 避免過早採用過度複雜的企業級架構。

## 3. 前端技術

### 3.1 React

採用 React 建立網站介面。

使用範圍：

- 品牌首頁。
- 登入、註冊及帳號管理。
- 學生學習中心。
- 教師管理中心。
- 管理員後台。
- 課程及教材介面。
- 題庫、練習及考試介面。
- AI 學習助理。
- 學習分析及遊戲介面。

### 3.2 TypeScript

採用 TypeScript 作為主要開發語言。

使用原因：

- 降低資料格式錯誤。
- 提升程式碼可讀性。
- 方便團隊共同開發。
- 讓前後端資料格式更容易保持一致。
- 有助於後續維護及擴充。

### 3.3 Vite

使用 Vite 作為前端開發及建置工具。

主要功能：

- 本機開發伺服器。
- 模組熱更新。
- 正式環境建置。
- 開發與部署設定管理。

### 3.4 CSS

第一階段使用 CSS Modules 或原生 CSS 管理樣式。

設計時遵守：

- 使用共用設計變數。
- 保持元件樣式獨立。
- 避免大量重複 CSS。
- 依照 RWD 規範調整版面。
- 維持品牌視覺一致性。

## 4. 後端技術

### 4.1 Node.js

使用 Node.js 執行後端服務。

負責：

- 使用者登入及註冊。
- 權限驗證。
- 課程及教材資料。
- 題庫及考試資料。
- 學習紀錄。
- AI 服務呼叫。
- 教師及管理員操作。

### 4.2 Express

使用 Express 建立 REST API。

API 應依功能模組分類，避免所有功能集中在單一路由檔案。

建議模組：

- auth
- users
- students
- teachers
- admins
- classes
- courses
- materials
- questions
- exams
- attempts
- learning-records
- analytics
- ai
- games
- announcements

### 4.3 API 設計原則

- 使用一致的 URL 命名規則。
- 使用適當的 HTTP 方法。
- 統一成功與錯誤回應格式。
- 驗證所有外部輸入。
- 不得信任前端自行傳送的角色或權限資訊。
- API 必須在伺服器端執行權限檢查。
- 敏感資料不得直接回傳給前端。

## 5. 資料庫技術

### 5.1 PostgreSQL

建議正式資料庫採用 PostgreSQL。

主要儲存：

- 使用者及帳號資料。
- 角色及權限。
- 班級及成員。
- 課程及教材。
- 題庫及題目選項。
- 考試及作答紀錄。
- 學習分析資料。
- 點數及遊戲紀錄。
- 公告及系統設定。

選擇原因：

- 支援關聯式資料。
- 適合多角色及多模組系統。
- 具備交易及資料完整性功能。
- 可支援未來較大的資料量。

### 5.2 Prisma

使用 Prisma 管理資料模型及資料庫操作。

用途：

- 定義資料表及關聯。
- 執行資料庫遷移。
- 產生型別安全的資料庫 Client。
- 降低手動撰寫 SQL 的錯誤風險。

### 5.3 開發資料庫

開發初期可使用 SQLite 作為本機測試或快速原型資料庫，但正式環境以 PostgreSQL 為目標。

正式上線前，必須完成資料模型、遷移及 PostgreSQL 相容性測試，不可直接假設 SQLite 與 PostgreSQL 的行為完全相同。

## 6. 身分驗證與安全技術

### 6.1 登入驗證

建議使用：

- JWT：管理登入授權資訊。
- HttpOnly Cookie：安全保存登入狀態。
- bcrypt：密碼雜湊。
- Google Identity Services：提供 Google 登入選項。

Google 登入仍需設定正式 OAuth Client、允許網域及伺服器端 Token 驗證。

### 6.2 角色與權限

平台至少包含：

- Student：學生。
- Teacher：教師。
- Admin：管理員。

權限必須由後端驗證，不得只依靠前端隱藏按鈕或頁面。

### 6.3 安全原則

- 密碼不得以明文儲存。
- API 必須驗證使用者身分。
- 重要操作必須檢查角色及資源所屬權限。
- 使用環境變數管理金鑰。
- 不得將 AI API Key 放在前端。
- 防止 SQL Injection、XSS、CSRF 等常見風險。
- 設定登入及 API 請求限制。
- 記錄重要管理操作。
- 正式環境使用 HTTPS。

## 7. AI 整合技術

### 7.1 AI Provider Layer

AI 功能採用可替換式服務架構，不讓平台核心程式直接依賴單一 AI 廠商。

建議設計：

- AI Provider Interface。
- AI Service。
- Prompt Template 管理。
- 輸入與輸出驗證。
- Token 使用量及成本紀錄。
- 錯誤處理及重試機制。
- AI 使用紀錄。

### 7.2 AI 功能範圍

第一階段：

- 題目概念解釋。
- 分層提示。
- 錯題分析。
- 學習方向建議。
- 課程內容輔助理解。

後續階段：

- 個人化學習路徑。
- 跨科目知識關聯。
- 教師教學輔助。
- 更進階的學習分析。

### 7.3 AI 安全原則

- AI 不應直接取代學生思考。
- 優先提供循序提示，而非直接給出所有答案。
- AI 回答需明確標示為 AI 生成內容。
- 對輸入內容進行必要檢查。
- 不將學生個人資料任意傳送至外部 AI 服務。
- 依年齡及教育情境設計適當的內容安全措施。
- AI 服務不可用時，平台基本學習功能仍應能使用。

## 8. 測試技術

### 8.1 Vitest

用於：

- 工具函式測試。
- 前端元件測試。
- 後端服務單元測試。
- 資料驗證測試。

### 8.2 Playwright

用於：

- 登入及註冊流程。
- 學生練習流程。
- 教師建立考試流程。
- 管理員權限測試。
- 響應式畫面測試。
- 主要使用者操作流程。

### 8.3 測試原則

- 每個核心功能都要有測試。
- 修正錯誤後應補上回歸測試。
- 不得只以畫面正常顯示判定功能完成。
- 重要權限必須測試未授權存取情境。
- 正式發布前必須通過建置及核心流程測試。

## 9. 版本控制與開發工具

### 9.1 Git 與 GitHub

使用 Git 管理版本，GitHub 作為遠端程式碼儲存庫。

原則：

- 功能開發使用分支。
- 提交訊息清楚描述修改內容。
- 重要功能完成後進行測試。
- 不提交 `.env`、密碼及 API Key。
- 合併前檢查程式碼及測試結果。

### 9.2 Antigravity

Antigravity 為主要 AI 輔助開發 IDE。

使用時必須遵守：

- 專案根目錄的開發規則。
- `.agents/rules/` 中的規則。
- `.agents/skills/` 中的技能流程。
- 不可未經檢查就接受 AI 修改。
- 不可讓 AI 自行宣稱未實際執行的測試已通過。

## 10. 跨平台擴充策略

第一階段先完成響應式網站，不同平台不應同時開發，以免增加維護成本。

| 階段 | 平台 | 規劃方向 |
| --- | --- | --- |
| 第一階段 | Web | 完成核心學習平台 |
| 第二階段 | Android | 評估 Flutter 或其他跨平台方案 |
| 第三階段 | iOS | 與行動版共用主要業務邏輯 |
| 第四階段 | Windows | 評估桌面應用程式方案 |
| 第五階段 | macOS | 與桌面版共用主要程式架構 |

跨平台技術最終選擇，應在網站核心功能穩定後，依實際需求及團隊能力決定。

## 11. 部署與維運方向

建議採用：

- Docker：建立一致的執行環境。
- 雲端主機：部署前後端服務。
- PostgreSQL：正式資料庫。
- HTTPS：加密傳輸。
- 環境變數：管理不同環境設定。
- 備份機制：定期備份重要資料。
- 日誌管理：追蹤錯誤及系統事件。

開發、測試及正式環境應分開管理，避免測試資料影響正式使用者。

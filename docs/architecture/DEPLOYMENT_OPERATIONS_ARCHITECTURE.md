## 1. 文件目的

本文件定義碼上學平台的開發環境、測試環境、正式環境、部署流程及日常維運方式。

主要目標：

1. 建立一致的開發與部署流程。
2. 避免開發環境與正式環境設定不一致。
3. 讓程式更新可以經過測試後再正式發布。
4. 保護資料庫、使用者資料及系統機密。
5. 建立資料備份與災難復原機制。
6. 監控系統運作狀況及錯誤。
7. 為未來跨平台服務及使用者成長預留擴充空間。

本文件是部署及維運規劃，不代表網站已經部署或正式上線。

## 2. 整體環境架構

平台分為三種主要環境：

| 環境 | 代碼 | 用途 |
| --- | --- | --- |
| 開發環境 | Development | 日常開發及功能建置 |
| 測試環境 | Staging | 整合測試及發布前驗證 |
| 正式環境 | Production | 提供實際使用者使用 |

### 2.1 開發環境

開發環境供開發者在本機執行程式。

預計使用：

- Node.js。
- npm。
- Vite。
- React。
- TypeScript。
- 後端 API。
- 本機或開發用資料庫。
- Antigravity IDE。
- Git。

開發環境不得直接使用正式環境的資料庫或正式機密設定。

### 2.2 測試環境

測試環境用於模擬正式環境。

主要用途：

- 前後端整合測試。
- API 測試。
- 資料庫測試。
- Google 登入測試。
- AI API 串接測試。
- 權限及安全測試。
- 使用者操作測試。
- 發布前驗收。

測試環境應使用獨立的資料庫及 API 金鑰。

### 2.3 正式環境

正式環境提供學生、教師及管理員使用。

基本要求：

- 使用 HTTPS。
- 使用正式資料庫。
- 使用安全的機密管理方式。
- 啟用錯誤監控。
- 定期備份資料。
- 設定 API 使用限制。
- 保留必要的系統稽核紀錄。
- 具備故障復原流程。

## 3. 系統部署架構

### 3.1 初期部署架構

```text
使用者
  │
  ▼
Web Browser
  │
  ▼
Frontend Hosting
  │
  ▼
Backend API Hosting
  │
  ├── Authentication
  ├── Course API
  ├── Question API
  ├── Exam API
  ├── Learning Analytics API
  └── AI Integration API
  │
  ├──────────────┐
  ▼              ▼
Database       AI Provider
  │
  ▼

```

### 3.2 部署原則

- 前端與後端可以分開部署。
- API 應有明確的正式及測試網址。
- 資料庫不得直接公開給瀏覽器。
- 外部 AI API 金鑰只能由後端管理。
- 檔案儲存應與一般程式部署分開考量。
- 所有正式服務必須使用安全連線。

### 3.3 初期與未來架構

初期以容易維護及控制成本為優先，不應過早採用複雜的微服務架構。

未來使用者數量增加時，再評估：

- 負載平衡。
- 多台 API Server。
- 快取服務。
- 背景工作佇列。
- 獨立 AI 服務。
- CDN。
- 資料庫讀取擴充。
- 容器化及自動化部署。

## 4. 部署平台選擇

正式選擇必須依實際費用、地區、服務限制、資料保護政策及技術相容性評估。

### 4.1 前端託管

候選服務：

- Vercel。
- Cloudflare Pages。
- Netlify。
- 其他支援靜態網站及前端部署的服務。

評估項目：

- 自訂網域。
- HTTPS。
- GitHub 自動部署。
- 環境變數管理。
- 建置時間。
- 流量及頻寬限制。
- 費用及免費方案限制。

### 4.2 後端託管

候選服務：

- Render。
- Railway。
- Fly.io。
- 雲端虛擬主機。
- 其他支援 Node.js 的服務。

評估項目：

- Node.js 相容性。
- 長時間執行能力。
- 資料庫連線。
- 環境變數管理。
- 日誌及監控。
- 自動部署。
- 備份及擴充能力。
- 費用。

### 4.3 資料庫服務

主要方向：

- PostgreSQL 託管資料庫。
- 支援自動備份的資料庫服務。
- 提供安全連線及權限管理的雲端資料庫。

正式環境不應只依賴開發者電腦中的 SQLite 檔案。

若目前程式仍使用 SQLite，應先評估現有資料結構、資料遷移及部署限制，再決定遷移時程。

## 5. 環境變數與機密管理

### 5.1 管理原則

以下資訊不得直接寫入公開程式碼：

- 資料庫連線字串。
- JWT 或 Session Secret。
- Google OAuth Client Secret。
- AI Provider API Key。
- 電子郵件服務密碼。
- 儲存服務金鑰。
- 第三方 API 憑證。

### 5.2 環境變數範例

```env
NODE_ENV=development
PORT=3000

DATABASE_URL=

SESSION_SECRET=

GOOGLE_CLIENT_ID=
GOOGLE_CLIENT_SECRET=

AI_PROVIDER_API_KEY=

EMAIL_HOST=
EMAIL_PORT=
EMAIL_USER=
EMAIL_PASSWORD=

FRONTEND_URL=
BACKEND_URL=
```

以上為欄位範例，不是可直接投入正式環境的設定。

### 5.3 機密安全要求

- `.env` 不得提交到 Git。
- `.env.example` 只保留變數名稱及必要說明。
- 正式環境使用託管平台的機密管理功能。
- 不在前端程式碼放置私密 API Key。
- 機密外洩時應立即撤銷及更換。
- 不在截圖、公開文件或錯誤訊息中暴露機密。

### 6.4 部署安全

- 正式環境部署應有權限限制。
- 不應讓未審核的程式直接進入正式環境。
- 正式部署應保留版本紀錄。
- 發布前應確認資料庫遷移安全。
- 發布失敗時應有回復方案。

## 7. 資料庫部署與遷移

### 7.1 資料庫環境隔離

開發、測試及正式環境必須使用不同的資料庫或明確隔離的資料空間。

不得讓測試程式誤刪正式資料。

### 7.2 Schema Migration

資料庫結構更新應透過版本化 Migration 管理。

基本要求：

- 每次變更都能追蹤。
- Migration 應經測試。
- 正式部署前確認影響範圍。
- 重要資料欄位變更前應備份。
- 不直接手動修改正式資料庫結構而不留下紀錄。

### 7.3 資料遷移

若從 SQLite 遷移至 PostgreSQL，應：

1. 確認現有資料表。
2. 檢查資料型別差異。
3. 規劃資料轉換。
4. 建立測試資料庫。
5. 執行資料匯入。
6. 驗證筆數及關聯。
7. 測試既有 API。
8. 完成正式切換。
9. 保留必要的回復方案。

## 8. 檔案與教材儲存

平台可能需要儲存：

- PDF 教材。
- 題庫附件。
- 圖片。
- 學生作品。
- 教師上傳的教材。
- 系統產生的報表。

建議使用物件儲存服務，而不是長期依賴 API Server 本機硬碟。

儲存需求：

- 權限控管。
- 私有檔案存取。
- 檔案大小限制。
- 檔案類型驗證。
- 備份及刪除政策。
- 必要時使用 CDN 提供公開教材。

## 9. 資料備份與災難復原

### 9.1 備份內容

- 使用者帳號資料。
- 班級及課程資料。
- 題庫及考試資料。
- 學習紀錄。
- 必要的 AI 對話紀錄。
- 教材及上傳檔案。
- 系統必要設定。

### 9.2 備份原則

- 定期執行資料庫備份。
- 重要檔案採用獨立備份。
- 備份資料應有存取權限限制。
- 備份檔應加密保存。
- 保留合理的歷史版本。
- 定期測試還原流程。
- 不將備份只存放在同一台伺服器。

### 9.3 RPO 與 RTO

RPO（Recovery Point Objective）：可接受的資料遺失時間範圍。

RTO（Recovery Time Objective）：可接受的系統恢復時間。

初期應依實際服務需求、預算及資料重要性制定目標，不應在未完成測試前承諾固定恢復時間。

### 9.4 還原測試

至少應驗證：

- 備份檔案完整。
- 資料庫可正常還原。
- 重要資料表及關聯正確。
- 檔案附件可以讀取。
- API 可以正常運作。
- 使用者可以正常登入。

## 10. 系統監控與錯誤追蹤

### 10.1 監控項目

| 類別 | 監控內容 |
| --- | --- |
| 前端 | 載入錯誤、JavaScript 錯誤 |
| 後端 | API 錯誤、回應時間 |
| 資料庫 | 連線狀態、查詢效能 |
| AI | 呼叫失敗、延遲、使用量 |
| 儲存 | 容量、上傳及下載錯誤 |
| 安全 | 異常登入、可疑 API 請求 |
| 部署 | 建置及發布結果 |

### 10.2 錯誤追蹤

可評估使用：

- Sentry。
- OpenTelemetry。
- 雲端平台內建日誌。
- 其他錯誤追蹤服務。

使用外部監控服務前，應確認資料蒐集範圍及個資保護設定。

### 10.3 健康檢查

後端應提供適當的健康檢查端點，例如：

```text
GET /health
```

健康檢查可確認：

- API Server 是否正常。
- 資料庫是否可連線。
- 必要服務是否可用。

健康檢查不得公開資料庫密碼、Token 或其他機密。

## 11. AI 服務維運

AI 功能可能受到外部服務狀態、API 額度及費用影響。

維運要求：

- 追蹤 AI API 使用量。
- 設定使用額度。
- 設定合理的請求頻率限制。
- 記錄呼叫成功及失敗狀況。
- 對外部服務逾時設定適當處理。
- 避免無限制重試。
- 設計服務暫時不可用時的替代提示。
- 不將 API Key 暴露在前端。
- 依需求評估 AI 模型及服務供應商。

AI 服務暫時不可用時，課程、題庫及一般練習功能應盡可能維持正常運作。

## 12. 系統更新與版本管理

### 12.1 版本管理

建議採用語意化版本：

```text
MAJOR.MINOR.PATCH
```

例如：

- 1.0.0：第一個正式版本。
- 1.1.0：新增功能。
- 1.1.1：錯誤修正。
- 2.0.0：重大架構更新。

### 12.2 發布紀錄

每次發布應記錄：

- 版本號。
- 發布日期。
- 新增功能。
- 修正內容。
- 資料庫變更。
- 已知問題。
- 回復方式。

### 12.3 回復策略

正式更新發生問題時，應能：

- 停止進一步發布。
- 回復上一個穩定程式版本。
- 檢查資料庫 Migration 是否可逆。
- 必要時執行資料還原。
- 通知受影響的使用者。

## 15. 維運與事件處理流程

### 15.1 事件分類

| 等級 | 說明 | 處理方向 |
| --- | --- | --- |
| P0 | 平台全面無法使用或重大資料風險 | 優先處理及啟動應變 |
| P1 | 核心功能大範圍異常 | 儘速修復 |
| P2 | 部分功能異常 | 安排修正 |
| P3 | 輕微問題或介面瑕疵 | 納入一般更新 |

### 15.2 事件處理流程

```text
發現異常
    │
    ▼
確認影響範圍
    │
    ▼
判斷事件等級
    │
    ▼
限制風險及保護資料
    │
    ▼
調查原因
    │
    ▼
修正問題
    │
    ▼
測試與驗證
    │
    ▼
恢復服務
    │
    ▼
記錄事件與改善措施
```

### 15.3 事件紀錄

應記錄：

- 發生時間。
- 影響功能。
- 影響使用者範圍。
- 事件等級。
- 問題原因。
- 處理方式。
- 恢復時間。
- 後續改善事項。

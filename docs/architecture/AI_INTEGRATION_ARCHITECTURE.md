## 1. 文件目的

本文件定義「碼上學 AI 智慧學習與教育科技平台」的 AI 整合架構，作為後續 AI API 串接、模型管理、提示詞設計、學習分析及安全測試的依據。

AI 不只是提供答案的聊天機器人，而是平台的智慧學習輔助核心。

主要任務：

1. 協助學生理解課程與知識概念。
2. 根據學生程度提供適當提示。
3. 分析學生的錯題及學習弱點。
4. 協助學生理解題目情境與解題方向。
5. 提供個人化複習建議。
6. 協助教師整理教學及班級學習資訊。
7. 支援未來不同科目與不同學習模式。

本文件為架構規劃，不代表 AI API 已經串接或功能已經完成。

## 2. AI 系統設計原則

### 2.1 核心理念

**AI 是學習教練，不是代寫答案的工具。**

系統應鼓勵學生先思考，再逐步取得協助。

### 2.2 設計原則

- 先理解問題，再提供協助。
- 優先提供提示，不直接公布答案。
- 根據學生程度調整解釋方式。
- 回答必須盡量依據平台教材與題目資料。
- 不確定的內容應明確說明。
- 避免產生虛構教材、錯誤答案或不存在的資料。
- AI 回答應能追蹤模型、提示詞版本及使用紀錄。
- 不同科目可以使用不同的提示詞與知識來源。
- 不向 AI 服務傳送不必要的個人識別資料。

## 3. AI 系統整體架構

AI 功能由前端、後端、AI 服務層及資料層共同組成。

### 3.1 架構流程

學生或教師操作平台後，由前端將需求傳送至後端 API。

後端依照使用者身分、角色、功能權限及使用限制進行驗證，再將請求交給 AI 服務層。

AI 服務層負責：

1. 判斷請求類型。
2. 選擇適合的 AI 模型。
3. 載入對應提示詞。
4. 取得必要的教材或題目資料。
5. 呼叫外部 AI API。
6. 檢查及整理 AI 回答。
7. 記錄使用量及錯誤狀態。
8. 將結果回傳給後端及前端。

### 3.2 系統架構示意

```text
學生／教師
    │
    ▼
前端 Web／Mobile／Desktop
    │
    ▼
Backend API
    │
    ├── 身分驗證與權限檢查
    ├── 使用頻率與額度檢查
    ├── 請求內容驗證
    │
    ▼
AI Service Layer
    │
    ├── Request Router
    ├── Model Manager
    ├── Prompt Manager
    ├── Context Builder
    ├── Knowledge Retrieval
    ├── Output Validator
    └── Usage & Cost Tracker
    │
    ▼
AI Provider API
    │
    ▼
回答整理與安全檢查
    │
    ▼
Backend API
    │
    ▼
前端顯示結果
```

## 4. AI 模型管理

### 4.1 模型選擇原則

平台不應將所有功能綁定單一 AI 模型。

應依照不同任務選擇適合的模型，並保留替換供應商的彈性。

| AI 任務 | 模型需求 |
| --- | --- |
| 一般課程問答 | 文字理解與解釋能力 |
| 數學及邏輯分析 | 推理與計算能力 |
| 程式碼輔助 | 程式理解與除錯能力 |
| 學習弱點分析 | 資料整理與分析能力 |
| 教材摘要 | 長文本理解能力 |
| 圖片題目分析 | 圖片理解能力 |
| 教師教學輔助 | 內容整理與生成能力 |

### 4.2 模型供應商

未來可評估：

- OpenAI API
- Google Gemini API
- Anthropic API
- 其他符合平台需求的 AI 服務。

實際使用哪一家服務，須依模型品質、費用、資料處理政策、服務穩定性及測試結果決定。

不得將尚未申請或尚未串接的 API 標示為已可使用。

### 4.3 Model Manager

建立統一模型管理層，避免在各個功能中直接寫死供應商 API。

管理項目：

- 供應商名稱。
- 模型名稱。
- 模型用途。
- API 端點。
- 請求參數。
- Token 限制。
- timeout。
- 重試策略。
- 使用狀態。
- 模型版本。

API Key 必須由伺服器端安全管理，不可放在前端程式碼或公開 GitHub 儲存庫。

## 5. AI 功能模組

平台初期規劃以下八項 AI 功能。

### 5.1 AI 學習助教

用途：回答學生在課程及學習過程中遇到的問題。

功能：

- 課程概念解釋。
- 關鍵字說明。
- 觀念比較。
- 例題解析。
- 延伸學習建議。
- 依學生程度調整回答。

回答應優先參考平台教材，並在適當情況下標示教材來源。

### 5.2 AI 分階段提示

此功能是平台的重要特色。

學生作答遇到困難時，AI 不直接公布答案，而是提供四個層級的協助。

| 層級 | 名稱 | 功能 |
| --- | --- | --- |
| Level 1 | 方向提示 | 提醒學生應注意的題目資訊 |
| Level 2 | 觀念提示 | 解釋相關知識及核心觀念 |
| Level 3 | 步驟提示 | 引導學生依序分析及解題 |
| Level 4 | 完整解析 | 提供完整解題過程與答案說明 |

設計規則：

- 預設從第一層開始。
- 學生可以自行選擇是否取得下一層提示。
- 每一層應提供不同程度的協助。
- 不應只將同一份答案切成四段。
- 完整解析應包含原因與觀念說明。
- 學生已經答對時，可提供觀念補充，而不是強迫繼續提示。

### 5.3 AI 題目理解分析

用途：幫助學生理解題目，而不只是得到正確答案。

分析內容：

1. 題目主要在考什麼。
2. 題目中的重要條件。
3. 關鍵字及專有名詞。
4. 題目涉及的知識點。
5. 容易誤解的地方。
6. 建議採取的思考方向。

### 5.4 AI 錯題分析

根據學生歷史作答紀錄分析：

- 常見錯誤題型。
- 經常答錯的知識點。
- 重複出現的錯誤。
- 作答時間較長的題目類型。
- 尚未掌握的章節。
- 建議優先複習的內容。

分析時應區分：

- 知識觀念不足。
- 題意理解錯誤。
- 計算或操作錯誤。
- 粗心或輸入錯誤。
- 資料不足，無法判斷。

AI 不應只憑單次錯誤就認定學生不懂某個知識點。

### 5.5 AI 個人化學習建議

根據學生的學習紀錄提供：

- 建議複習章節。
- 推薦練習題。
- 建議學習順序。
- 需要加強的觀念。
- 學習進度提醒。

建議應能連結到平台實際存在的課程或題目，不可推薦不存在的教材。

### 5.6 AI 程式碼輔助

主要支援程式設計及網頁實作學習。

功能：

- 解釋 HTML、CSS、JavaScript。
- 分析程式碼錯誤。
- 說明錯誤原因。
- 提供除錯方向。
- 解釋網頁排版及互動邏輯。
- 協助學生理解程式結構。

預設以解釋與引導為主，避免學生只複製程式碼而不了解內容。

### 5.7 AI 教師教學輔助

提供教師使用的輔助功能：

- 課程內容整理。
- 題目分類建議。
- 學習成果摘要。
- 班級弱點分析。
- 教材重點整理。
- 題目難度初步建議。

AI 產生的題目、答案及分析必須經過教師或適當的驗證流程，不能直接視為正確教材。

### 5.8 AI 學習摘要

在學生完成練習或測驗後，整理：

- 本次練習內容。
- 答題表現。
- 主要錯誤類型。
- 已掌握的觀念。
- 尚需加強的知識點。
- 下一步學習建議。

摘要應以簡潔、容易理解為主，不需要產生過度冗長的深度報告。

## 6. Prompt Manager（提示詞管理）

### 6.1 設計目的

統一管理不同 AI 功能使用的系統提示詞，避免提示詞散落在各個程式檔案中。

### 6.2 提示詞分類

建議分類：

```text
ai/
├── prompts/
│   ├── system/
│   │   ├── base.md
│   │   └── safety.md
│   ├── tutor/
│   │   ├── learning-assistant.md
│   │   └── concept-explanation.md
│   ├── hints/
│   │   ├── level-1.md
│   │   ├── level-2.md
│   │   ├── level-3.md
│   │   └── level-4.md
│   ├── analysis/
│   │   ├── question-analysis.md
│   │   ├── wrong-answer-analysis.md
│   │   └── learning-summary.md
│   ├── coding/
│   │   ├── code-explanation.md
│   │   └── debugging.md
│   └── teacher/
│       └── teaching-assistant.md
```

以上為建議目錄，實際位置須與專案既有資料夾結構整合。

### 6.3 提示詞版本管理

每份提示詞應記錄：

- Prompt ID。
- 版本編號。
- 使用功能。
- 建立時間。
- 更新時間。
- 修改原因。
- 測試結果。

修改提示詞時應保留版本紀錄，避免更新後無法追查回答品質變化。

## 7. Context Builder（上下文管理）

### 7.1 目的

讓 AI 在回答時取得必要的學習情境。

可使用的上下文：

- 使用者目前學習科目。
- 目前課程與章節。
- 題目內容。
- 題目知識點。
- 學生目前的作答內容。
- 學生已取得的提示層級。
- 經授權可使用的學習紀錄。
- 相關教材內容。

### 7.2 上下文使用原則

- 只傳送完成任務必要的資料。
- 不應將所有歷史對話無限制傳送。
- 不應任意傳送學生個人識別資訊。
- 不同使用者的資料必須隔離。
- 上下文應設定長度限制。
- 不可信任的教材或使用者輸入不得覆蓋系統規則。

## 8. Knowledge Retrieval（教材檢索）

### 8.1 設計目的

避免 AI 只依靠模型原本的知識回答，導致教材內容不一致或產生錯誤資訊。

平台應逐步建立以自有教材與題庫為依據的檢索系統。

### 8.2 初期方式

MVP 可先採用：

- 依科目查詢教材。
- 依章節查詢內容。
- 依題目 ID 取得題目資料。
- 將相關文字內容提供給 AI。
- 回答中標示使用的教材來源。

### 8.3 後續擴充

未來可導入 RAG（Retrieval-Augmented Generation，檢索增強生成）。

規劃流程：

```text
教材上傳
    │
    ▼
文字擷取與整理
    │
    ▼
內容分段
    │
    ▼
Embedding 向量化
    │
    ▼
向量資料庫
    │
    ▼
依問題檢索相關內容
    │
    ▼
組合上下文
    │
    ▼
AI 產生回答
    │
    ▼
附上教材來源
```

向量資料庫的實際選擇可於技術驗證階段評估，例如 PostgreSQL 搭配 pgvector。

### 8.4 教材來源管理

教材應保存：

- 教材 ID。
- 科目。
- 章節。
- 文件名稱。
- 來源位置。
- 版本。
- 授權狀態。
- 更新時間。

不得將未取得使用授權的教材任意提供給 AI 或公開使用。

## 9. AI 回答品質管理

### 9.1 回答驗證

AI 回答送出前，應依功能進行適當檢查：

- 是否有空白或格式錯誤。
- 是否符合預期資料結構。
- 是否超過長度限制。
- 是否包含不允許的內容。
- 是否引用不存在的教材。
- 是否洩漏其他使用者資料。
- 是否出現明顯不合理的答案。

### 9.2 結構化輸出

需要固定格式的功能，應使用結構化資料，例如 JSON Schema 驗證。

錯題分析的輸出可規劃為：

```json
{
  "summary": "本次練習主要錯誤集中於版面配置觀念。",
  "weaknesses": [
    {
      "topic": "CSS 排版",
      "confidence": "medium",
      "evidenceCount": 3
    }
  ],
  "recommendations": [
    {
      "type": "review",
      "title": "複習 CSS Flexbox",
      "reason": "近期相關題目出現多次錯誤。"
    }
  ]
}
```

以上僅為資料格式示意，實際內容必須由系統依真實資料產生。

### 9.3 品質測試

建立固定測試題組，檢查：

- 正確性。
- 解釋清楚程度。
- 提示層級差異。
- 教材依據。
- 回答一致性。
- 安全性。
- 不確定內容的處理方式。

每次更換模型或更新 Prompt，都應重新執行測試。

## 10. AI 安全機制

### 10.1 輸入安全

- 驗證輸入長度及格式。
- 限制不合理的請求頻率。
- 防止提示詞注入影響系統規則。
- 對教材內容與使用者輸入進行信任分級。
- 避免傳入不必要的敏感資料。

### 10.2 輸出安全

- 適當檢查不安全內容。
- 防止個人資料外洩。
- 不提供未授權的考試答案。
- 不將 AI 推測當成確定事實。
- 對高風險內容採取額外檢查。
- 提供錯誤回報及人工檢視機制。

### 10.3 學習公平性

AI 不應：

- 因學生程度不同而給予不合理待遇。
- 只根據一次作答結果判定能力。
- 將 AI 分析當成正式學業評量。
- 未經授權提供其他學生的學習資料。
- 代替教師做出需要人工判斷的重要決策。

## 11. Token 與成本控管

### 11.1 使用量紀錄

每次 AI 請求應記錄：

- 使用者 ID。
- 功能類型。
- AI 供應商。
- 模型名稱。
- 輸入 Token。
- 輸出 Token。
- 請求時間。
- 回應時間。
- 執行狀態。
- 預估成本。

### 11.2 成本管理策略

- 依任務選擇適合模型。
- 簡化不必要的上下文。
- 設定輸入及輸出長度限制。
- 對重複且穩定的內容評估快取。
- 設定使用者及班級使用額度。
- 定期檢查模型費用。
- 遇到異常用量時暫停或限制服務。

### 11.3 使用限制

限制可依以下條件設定：

- 每日請求次數。
- 每月 Token 額度。
- 單次請求最大 Token。
- 不同角色使用權限。
- 不同功能使用額度。

實際數值應在 API 成本測試後決定，不先設定沒有依據的固定價格。

## 12. AI 錯誤處理與服務穩定性

### 12.1 常見錯誤

| 錯誤 | 處理方式 |
| --- | --- |
| API Key 無效 | 停止請求並記錄錯誤 |
| API 逾時 | 依策略有限次重試 |
| 超過使用額度 | 提示稍後再試或使用額度不足 |
| 模型服務中斷 | 啟用可用的替代方案或提示服務暫時不可用 |
| 回傳格式錯誤 | 驗證失敗後有限次修正或回報 |
| 使用者輸入過長 | 提示縮短內容 |
| 網路中斷 | 保留必要的請求狀態並允許重新操作 |

### 12.2 重試原則

- 僅對可重試錯誤進行重試。
- 設定最大重試次數。
- 使用適當的退避等待策略。
- 避免重複扣除使用額度。
- 不因錯誤而無限制呼叫模型。

### 12.3 服務狀態

前端應清楚顯示：

- 正在產生回答。
- 回答完成。
- 服務暫時無法使用。
- 使用額度不足。
- 請求失敗，可重新嘗試。

不得在 AI API 尚未成功回應時，假裝已經產生回答。

## 13. AI 資料紀錄與隱私

AI 對話及使用紀錄應依平台隱私政策管理。

基本原則：

1. 只保存必要紀錄。
2. 明確告知使用者資料用途。
3. 限制教師及管理員的資料存取範圍。
4. 避免保存不必要的敏感資訊。
5. 不將 API Key 或存取 Token 寫入日誌。
6. 依適用法規及平台政策設定保存期限。
7. 提供必要的資料查詢、更正及刪除流程。
8. 外部 AI 供應商的資料處理條款必須事先確認。

## 14. AI API 介面規劃

建議統一由後端提供以下 API。

| Method | Endpoint | 用途 |
| --- | --- | --- |
| POST | `/api/ai/chat` | 一般 AI 助教 |
| POST | `/api/ai/hints` | 取得分階段提示 |
| POST | `/api/ai/question-analysis` | 題目理解分析 |
| POST | `/api/ai/wrong-answer-analysis` | 錯題分析 |
| POST | `/api/ai/learning-recommendations` | 個人化學習建議 |
| POST | `/api/ai/code-review` | 程式碼輔助 |
| POST | `/api/ai/learning-summary` | 學習摘要 |
| GET | `/api/ai/usage` | 查詢個人使用量 |

### 14.1 API 設計原則

- 所有 API 必須經過後端身分驗證。
- 驗證使用者是否具有該功能的權限。
- 驗證輸入資料及請求長度。
- 設定請求頻率限制。
- 使用統一錯誤格式。
- 不向前端暴露供應商 API Key。
- 不讓前端自行指定未授權的模型或系統提示詞。

### 14.2 分階段提示 API 示意

請求：

```json
{
  "questionId": "question-uuid",
  "hintLevel": 1,
  "attemptId": "attempt-uuid"
}
```

回應：

```json
{
  "success": true,
  "hintLevel": 1,
  "content": "先找出題目中最重要的條件，再思考它對應的觀念。",
  "nextLevelAvailable": true
}
```

上述 UUID 僅為格式示意，正式系統應使用真實資料庫 ID，並由後端驗證使用者是否有權存取該題目及作答紀錄。

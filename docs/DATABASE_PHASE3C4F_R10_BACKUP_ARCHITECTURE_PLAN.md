## 三、異地備份方案比較與架構選型

針對 CODE TO KNOW 之**學生專題、零預算 ($0.00 USD)** 與雲原生架構，比較 4 種主流備份方案：

| 評估維度 | 方案 A：GitHub Actions 定時備份 | 方案 B：外部排程觸發 Webhook | 方案 C：Supabase 平台內建備份 | 方案 D：GitHub Actions + Cloudflare R2 (推薦) |
| :--- | :--- | :--- | :--- | :--- |
| **額外費用** | **$0.00** (公開無限/私有 2,000分/月) | **$0.00** | **需升級 Pro ($25/月)** | **$0.00 (完全免費)** |
| **免費額度限制** | 每月 2,000 分鐘建置時間；Artifact 留存最長 90 天 | Render 免費 Webhook 有 100s 逾時與休眠冷啟動延遲 | **Free Tier: 0 天留存，無自動快照，無 PITR** | R2 提供 10GB 免費儲存/月，**$0 出流量費用** |
| **排程可靠度** | 高 (每日標準 Cron，容許 15~30 分鐘抖動) | 中 (受後端服務休眠與連線逾時影響) | 高 (平台託管，但本專案不適用) | **高 (由 GitHub Runner 獨立排程執行)** |
| **備份檔案大小** | 適合中小規模 (< 500MB) | 差 (HTTP 傳輸大型 Dump 易逾時中斷) | 平台全量 | **極佳 (支援分塊加密與大檔傳輸)** |
| **異地獨立性** | 中 (集中於 GitHub 基礎設施) | 低 (集中於應用伺服器) | **無 (同區域鎖定，非使用者可控異地)** | **極高 (跨 GitHub 與 Cloudflare 雙異地)** |
| **機密安全管理** | 透過 GitHub Secrets 管理憑證，安全嚴密 | 需在後端曝露備份端點，風險較高 | 平台內部管理 | **透過 GitHub Secrets 加密，Runner 不落地** |

### 建議架構結論：採用「方案 D（GitHub Actions + Cloudflare R2 異地冷存儲）」
- **選型理由**：
  1. **零成本嚴格遵守**：GitHub Actions 免費時數每月足夠執行每日 3 分鐘備份作業；Cloudflare R2 免費提供 10GB 儲存空間與 0 元出流量費（專案 Dump 僅 500KB，10GB 可存儲超過 20,000 份備份）。

  3. **自動化告警**：執行失敗時由 GitHub Actions 即時發送 Email 通報 DBA。

## 六、備份安全性與還原風險控制

### 1. 備份檔案敏感度認知
- 資料庫 Dump 包含實體資料：使用者帳號（Email）、顯示名稱、Bcrypt 密碼雜湊、Session TokenHash、電子郵件驗證憑證、教師審核證明與 AuditLog 紀錄。
- **原則：必須將備份檔案視為等同正式資料庫之最高敏感等級資料！**

### 2. 加密與金鑰分離管理
- **傳輸加密**：`pg_dump` 連線強制 `PGSSLMODE=verify-full`。
- **儲存加密 (Encryption at Rest)**：在 GitHub Runner 內部使用 AES-256-CBC 與 PBKDF2 進行對稱加密：
  ```bash
  openssl enc -aes-256-cbc -salt -pbkdf2 -in database.dump -out database.dump.enc -pass pass:$BACKUP_ENCRYPTION_KEY
  ```
- **金鑰保管**：`BACKUP_ENCRYPTION_KEY` 存放於 GitHub Repository Secrets，**嚴禁存放於備份檔案所在之物件存儲空間中**。

### 3. 防止未授權下載與惡意刪除
- Cloudflare R2 / S3 Bucket 權限設為私有 (Private)，關閉公開訪問。
- 設定物件版本控制 (Object Versioning) 或 Object Lock，防止備份遭勒索軟體覆蓋或惡意抹除。

### 4. 防止正式環境遭誤還原覆蓋 (Accidental Overwrite Protection)
- 還原工具必須在邏輯層面**嚴格禁止以生產庫 Host 為預設目標**。
- 還原作業必須預設指向隔離沙盒容器（如 `127.0.0.1:5433`），若欲針對生產庫還原，必須滿足：
  1. 顯式指令參數 `--force-production-restore`。
  2. 互動提示輸入專案 Project Ref 進行二次手動文字確認。
  3. 雙人授權與維護公告確認。

## 七、未來自動化排程架構設計 (12 步管線規劃)

```
[01. 觸發] GitHub Actions Scheduled Workflow (每日 03:00)
    │
    ▼
[02. 權限] 自 GitHub Secrets 安全注入 DATABASE_URL 與 ROOT CA (記憶體暫存)
    │
    ▼
[03. 傾印] 啟動固定 Digest 之 PostgreSQL 17 Client 容器執行 pg_dump (-Fc, verify-full)
    │
    ▼
[04. 核查] 驗證 exit_code == 0 且檔案大小 > 0，執行 pg_restore --list 結構檢查
    │
    ▼
[05. 雜湊] 計算未加密 Dump 之 SHA-256 數位指紋
    │
    ▼
[06. 加密] 使用 BACKUP_ENCRYPTION_KEY 執行 AES-256-CBC 加密，產出 .dump.enc
    │
    ▼
[07. 再驗] 計算加密後 .dump.enc 之 SHA-256 雜湊
    │
    ▼
[08. 上傳] 透過 S3 相容 API 將加密檔與 metadata JSON 串流上傳至 Cloudflare R2 / 異地空間
    │
    ▼
[09. 比對] 驗證遠端 ETag / 上傳位元組數與本地一致
    │
    ▼
[10. 紀錄] 產出備份記錄摘要 (Metadata JSON, 絕不記錄密碼)
    │
    ▼
[11. 通報] 若失敗發送 Email / Webhook 警報；若成功記入 GitHub Summary
    │
    ▼
[12. 輪轉] 依保留政策清除超過 7 天之每日過期備份物件
```

## 九、尚未解決之安全風險與限制

1. **GitHub Secrets 暴露風險**：若 GitHub Repository 權限管理不當，具備 Write 權限之人員可能透過修改 Workflow 印出環境變數。因此專案必須嚴格管理 Repository Collaborators 權限，啟用 Branch Protection。
2. **Supabase 7 天閒置暫停風險**：若專案連續 7 天無活動，資料庫進入休眠，定時備份可能因連線逾時失敗。需依 R8 建議設定定時心跳端點保持連線活躍。
3. **異地備份目前尚未正式建置**：本階段為**技術規劃**，在正式切換前，專案團隊仍需手動將 `code_to_know_supabase_prod.dump` 上傳至第二處實體（如 Google Drive）作為應急備份。
